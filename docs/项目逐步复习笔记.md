# 司契（siqi）AI Agent研发平台详细复习

## 1、为什么要做这个项目，主要是往哪里考虑的

「这个项目的起点是我发现一个矛盾：**AI 写代码已经没问题了，但企业还是不敢让它端到端做完一个任务。**

我把原因归结成一句——**不是模型能力不够，是出了事说不清**。具体三个说不清：它当时看了什么、为什么这么改、谁批的。

我查了一圈现有工具，发现它们的形状都是**会话级、个人级**的：能力很强，但记录留在开发者本机，组织层面拿不到。

**所以我判断，要做的不是更强的编码 Agent，是它外面那一层责任链。** 这就是为什么我把整个平台按『**约束在前，生成在后**』来设计。」



重点解决「**企业如何放心使用 AI 参与研发**」的问题。
其实做这个项目的初衷也很简单，我的目标行业是**AI Agent应用开发**，所以做技术选型时我一直按**企业采购标准**要求自己：私有化部署、数据不出内网、模型可替换、审计可追溯
企业已经在用 AI 改代码了，这点不用讨论——Cursor、Copilot、Claude Code 都在改。

但现在的用法有个共同形状：**AI 在人的环里逐行干活**。工程师坐那儿看着它改，逐块确认，改完提 PR。这条路通，是因为**责任还在人身上**。

没通的是另一件事：**把整个任务交给 AI 端到端做完**。这时候责任链断了——它不是「这一行改得对不对」，而是「**这个任务该不该这么改、范围对不对、谁批的、三个月后能不能复盘**」。

而且这些工具都是**个人级**的：CTO 拿不到一张控制面，不知道团队里 AI 改了多少、碰了哪些仓库、有没有绕开审批。

我做的是**从个人级到组织级的那一层**。所以我的设计原则只有一条：**约束在前，生成在后**——不是让 AI 更聪明，是让 AI 的每一步**可审批、可回放、可追责**。



**先说结论**：企业用 AI 改代码，卡点不在「AI 会不会写」，而在「**出了事谁说得清**」。

**举个场景**。一个工程师让 AI 修支付回调的 bug。AI 改完了，测试过了，PR 也提了。三个月后线上出问题要复盘，三件事说不清：它当时看了哪几个文件、哪些行？它为什么这么改？这个改动范围是谁批的？——日志早就散了。

**为什么现有工具不够**。Cursor、Claude Code 这些我平时也用，它们很好。但它们有个共同的形状：**AI 是在人的眼皮底下干活**——工程师坐那儿一行行看着它改，改完提 PR。责任还在人身上，所以这条路是通的。

通不了的是另一件事：**把一整个任务交给 AI 做完**。这时没人一行行盯着，责任链就断了。而且这些工具的记录是**会话级、留在开发者本机**的——组织层面要统一查「AI 到底参与了哪些改动」，得自己搭。

**我做了什么**。整个平台只有一条原则：**约束在前，生成在后**。具体三条：

一、**AI 不能直接改代码**。它只能先写一份「改动计划」——打算动哪几个文件、每步做什么。计划先过风险判断，人批了才允许生成 Diff。

二、**检索必须留痕**。我把每段代码的来源绑死在 commit 和行号上，所以事后能还原「当时它看到了什么」。我们内部叫**上下文可回放**——这是直接读文件的用法做不到的，它们读完就散了。

三、**做不了就说做不了**。企业版我禁止静默降级：检索或模型不可用就直接报错，绝不退回无边界检索。没验证过的能力我也专门写了份边界声明，不写进承诺。

**最后说边界**。我也清楚它不适合谁：小团队用 CI 加 PR 审批就够了。我这套的价值，只在**需要事后追责和跨人审批**的场景。



**反驳点**：面试官再说「企业早就在用了」，你可以直接接——「对，所以我说的不是敢不敢用，是**用了之后组织能不能管、出事能不能举证**」。**反驳变成了你的论证台阶。**

## 2、前端为什么要用Vue3框架，而不是其他框架，对比Vue2，有什么区别

面试官问这题，其实在测**四件事**

| 他想知道                              | 对应你的答法                  |
| ------------------------------------- | ----------------------------- |
| 1. 你有没有**理由**（还是跟着教程走） | 给出具体机制，不是形容词      |
| 2. 你知不知道**你失去了什么**         | **主动说代价** ← 最能加分     |
| 3. 你会不会说**外行话**               | 绝不说「Vue 更简单/性能更好」 |
| 4. 你什么情况下会**选另一个**         | 给判断边界                    |

主回答（面试口播版，约 70 秒）

> 先说实话：**这个选择我没当成核心决策**——它是个内部中后台，框架在这个场景里差异没那么大。但选 Vue 我有四条具体理由，我也清楚代价。
>
> **第一，这个项目用不上 React 最大的优势场景。** React 最值钱的地方是 Next.js 那套——SSR、SEO、Server Components。而我是 20 个页面的内部管理台，**全部登录后才可见，SEO 和首屏 SSR 价值是零**。所以选 React 的一个主要理由自动就不存在了。
>
> **第二，响应式不用手写依赖数组。** 我有个组件 `AppShell.vue` 1268 行，里面侧栏要按权限过滤——而权限来自**两套异步源**：团队角色和企业角色。Vue 里我用 `computed` 派生，它自动追踪这两个源，任一变了就重算。**这在 React 里就是 `useMemo` 加依赖数组，漏一个依赖就是 UI 不更新**——那是 React 最经典的 bug 类型。我不用花精力在这上面。
>
> **第三，我是三层权限驱动渲染**：路由守卫、侧栏过滤、按钮级控制。Vue 的 `v-if` 比 React 的条件渲染三元嵌套好读，我专门封了个 `PermissionGate` 组件。
>
> **第四，Element Plus 把中后台的重组件直接覆盖了**——表格、抽屉、时间线、标签、Diff 展示，我页面里全是这些。React 侧得自己组合 antd 加一堆周边，**这是实打实的时间成本**。
>
> **代价我也清楚**：React 在复杂可视化、富文本、拖拽这类库上生态更大、迭代更快；社区和岗位规模也更大。**还有一个我自己的债**——我 `frontend/src/style.css` 单个文件 409KB，那是**我没做 CSS 分层**，跟框架无关，但确实是我没做好。
>
> **如果换场景我会选 React**：要做有 SEO 的官网或内容站，我会上 Next.js；如果团队本来就是 React 团队，我也不会折腾。

三个必被追问的问题，先准备

**① 「Vue 和 React 的响应式到底差在哪？」**（技术题，答好很加分）

> Vue 3 用 **Proxy 做细粒度依赖追踪**，运行时知道**哪个组件用了哪个数据**，变了只更新用到它的地方；React 是 **setState + 不可变数据**，靠重新执行组件函数 + **协调（reconcile）和 diff** 找出变化。
>
> 差别落在开发者身上就是：**Vue 不用声明依赖，React 要手写依赖数组**——`useEffect`/`useMemo` 漏依赖会导致闭包拿到旧值。Vue 的代价是**响应式数据被追踪，调试时链路不如 React 显式**。

**② 「那 React 你熟吗？」** ← **这题必须诚实**

- **如果熟**：「我自己也写过 React，hooks 和状态管理我用过」——然后**别多说**，等他问。
- **如果不熟**：「Vue 我做到能主导架构。React 我能读、能改、能上手项目，但**没到能主导架构的程度**。」

⚠️ **不熟就别装。** 「我 Vue 做得深，React 需要上手时间」**比吹牛安全一百倍**——吹牛会当场被三个问题打穿。

**③ 「如果让你用 React 重写，你会怎么做？」**

> 结构不用大改：**Pinia 换 Zustand 或 Redux Toolkit，路由换 React Router，Element Plus 换 antd**。 真正要重做的是**权限驱动渲染**那块——`v-if` 要改成条件渲染加 `useMemo`，**而且依赖数组得仔细维护**，这是我刚才说的那个坑。大概两到三周。

## 3、后端你为什么要用FastAPI的框架

面试答法（口播约 60 秒）

> 先定性：这不是「最好」，是**最匹配**。
>
> 我这个项目是**前后端分离的 API 服务**，97 个接口，前端是 Vue。所以我要的三件事：**请求校验、接口契约、认证接入**。FastAPI 正好三样都内置：Pydantic 声明即校验，OpenAPI 自动出文档——**我这次核对接口清单就是直接读 `/openapi.json`**，97 条路径；认证是 `Depends(get_current_user)` 一行接入。
>
> **Django 的问题不是不好，是它给多了**：Admin、模板、内置 Auth 我都不需要，而它的 DRF Serializer 会让我把字段定义写第二遍。**Flask 的问题是给少了**：校验、文档、依赖注入都得自己拼，规模化后每个项目一套架构。
>
> **但我得说清两件我自己的事。**
>
> 第一，**我选 FastAPI 不是为了 async**。我的业务代码 **100% 同步**，`async def` 只有两个，都是框架中间件和 lifespan。因为我的瓶颈不是 I/O 并发，是 LLM 调用和测试执行这种**分钟级长任务**——async 解决不了，我把它们丢给 Celery 了。**API 层同步 + 队列层异步**。
>
> 第二，**FastAPI 的自由度我付出代价了**：我的 `main.py` 有 9177 行。Django 的 app 约定会强制我拆开，FastAPI 不会。**这是我的问题**，重做的话我会按领域拆 router，把服务函数下沉到 services。
>
> **换场景我会换**：如果是内容型站点、要 Admin 后台、团队十来个人，我会用 Django；如果就是个小服务或要完全自控技术栈，我用 Flask。

三个必被追问的问题

**① 「那你为什么不用 async？」** → 用上面那段「瓶颈是分钟级长任务，所以用 Celery」。

**② 「`main.py` 9177 行，你怎么维护？」** → **不要辩解**。承认 + 给拆分方案 + 说清这是框架自由度的代价。**这题答好了反而是加分项。**

**③ 「为什么用 Python 不用 Go/Java？」**

> 「因为**生态**，不是性能。LangChain、LangGraph、LlamaIndex、DeepAgents、pymilvus —— 我这套 RAG 和 Agent 编排依赖的库**全是 Python**，Go 和 Java 没有对等替代。**这个项目的瓶颈在模型调用和检索质量，不在语言性能**，所以为性能换语言是错的方向。」

## 4、数据库上你为什么要用MySQL而不是PostgreSQL

面试答法（口播约 70 秒）

> 我先把这个问题的前提拆一下：**「企业级」不等于「必须 PostgreSQL」**。国内互联网和企业中台，MySQL 是绝对主流；PostgreSQL 更多出现在金融、电信这类偏核心系统的场景。**我的客户是企业研发团队，属于前者。**
>
> 然后说我的判断依据。**PostgreSQL 最大的卖点之一是 pgvector，而我没有用数据库存向量** —— 向量我放在 Milvus，MySQL 只管业务事务和审计，两者靠 `chunk_id`、`index_id`、`commit_sha` 关联。**所以这个卖点对我自动失效。**
>
> 更重要的是，**我把能力全放在应用层，不依赖数据库的高级特性**：多租户隔离是 `tenant` 只从服务端上下文取；审计是双表；迁移有 fail-closed 状态机；多副本抢占用的是**条件 UPDATE 的乐观并发**，不是数据库特有的锁。**「企业级」是我架构给的，不是数据库给的。**
>
> 而且我刻意保持了可移植性 —— 用 SQLAlchemy 加 Alembic，**同一份代码我在 SQLite 和 MySQL 上都跑过，只换 `DATABASE_URL`**。所以换数据库不是重写。
>
> **但我也清楚 PostgreSQL 在我这个项目里确实更强的地方，有两点我甚至踩过坑**： 一是 **JSONB**。我把很多结构化数据存在 JSON 列里，查不动，所以不得不**再建一张宽表**来查询 —— 代价是同一份数据有两套表示，**我实测就出现过两边不一致**。如果有 JSONB，可能一份就够。 二是 **`TEXT` 的默认值**。我做 MySQL 迁移时，`TEXT DEFAULT ''` 直接被 MySQL 拒了（报 1101），只能改成没有默认值。**PostgreSQL 是允许的。** 另外 PostgreSQL 的**声明式分区**对我这种只增不改的审计大表更友好 —— 我审计事件已经到十万量级了。
>
> **所以结论是**：MySQL 是我在「用不到 PG 高级能力 + 国内运维生态」下的正确选择；但如果我的向量不走 Milvus、或者审计表要继续涨到亿级、或者团队本来就熟 PostgreSQL，**我会换成 PostgreSQL**。



三个必被追问的问题（**第一个最关键**）

### ① 「那你为什么不用 pgvector，省掉 Milvus 一个组件？」

**这是本题最大的陷阱**——面试官会说「你这不是多维护一个组件吗」。答法：

> pgvector 适合**中小规模**（十万级向量以内）和想少维护一个组件的场景。我不选它有三个具体原因：
>
> 一、**规模**。企业仓库的切片量会是百万级，专用向量库的分片和独立扩缩容能力更合适； 二、**我需要混合检索**。我是 BM25 + 向量 + RRF 融合，**词法检索那一半 pgvector 给不了**，还得回数据库做全文索引，反而更绕； 三、**我需要强过滤**。企业 RAG 必须按租户、项目、仓库、commit **四个维度**先约束候选集再检索 —— Milvus 的「过滤 + 向量」组合能力比 pgvector 成熟。
>
> 另外我本地用的是 **`milvus-lite`**（嵌入式，在依赖清单里），**开发时不需要起容器**，所以维护成本没想象中高。

### ② 「`audit_events` 已经十万条了，这种表怎么处理？」

**不要硬撑。** 诚实答：

> 现在是靠**索引加分页**，还没做分区 —— 这是我明确的待办。企业规模该做的是：**按月声明式分区 + 冷热分离**，热数据留 3 个月在线，冷数据归档到对象存储，审计查询走单独只读副本。**PostgreSQL 在这块比 MySQL 成熟，这是我承认的短板。**

### ③ 「MySQL 和 PostgreSQL 默认隔离级别差别？」→ 用第三节 ④ 那段答。

| A3   | 为什么要工作流？一个精心写的大 prompt 不行吗？               | 你懂不懂可维护性     |
| A4   | Agent 为什么不能直接改代码？                                 | 你有没有安全意识     |

**A2 是必答的，你的代码里有现成答案**——`workflow.py` 文件头 `:6-12` 自己写明了职责边界：

> 「LangChain（`model_config`）负责**模型调用与结构化输出**；DeepAgents 负责 **Agent 能力封装**；状态流转、阶段路由、审批暂停/恢复、失败分流由**本图承载**。」

**标准答法**：

> LLM 是**推理大脑**；Workflow 是**固定剧本流水线**；Agent 是带大脑，能自主规划、调用工具、动态调整方案的智能实体。 Workflow 步骤写死；Agent 是动态决策；LLM 是底层基础，Workflow 和 Agent 都可以基于 LLM 搭建.



> LangChain 是**模型和工具的抽象层**——我用它做模型调用（`ChatOpenAI` / `init_chat_model`）和结构化输出；LangGraph 是**状态图编排**——负责节点、条件边、checkpoint。 **我没有用 LangChain 的 AgentExecutor**，因为它是一个**循环**：模型自己决定调什么工具、什么时候停。**我要的是固定拓扑 + 可审批 + 可回放**，所以用 LangGraph 的 StateGraph 把流程画出来，模型的自由度只保留在**节点内部**。

#### ⭐ B2 是你的"踩过坑"证据，答出来很硬

你的 `AgentFlowState` 里有这么一行（`graph.py:34`）：

python



```
_latest_artifact: dict | None  # 需声明，LangGraph 才会把该键传入节点（否则被丢弃）
```

**这句话只有真踩过坑的人才写得出来。** 答法：

> state 是 `TypedDict`，但 **LangGraph 只把「在 StateGraph 构造时注册过的键」传给节点**。我一开始想动态塞一个 `_latest_artifact` 进 state 传给路由函数，结果**节点里读不到**——因为没在类型声明里注册，LangGraph 把它丢了。所以我在 `AgentFlowState` 里**显式声明了它**，还留了注释防止以后被清理掉。
>
> 这是我这个项目里最典型的"文档没写、只能踩"的坑。

#### B4 的答法

> checkpoint 存的是**流程恢复点**（走到哪个节点、状态是什么、下一步该做什么），不是业务数据。业务数据在任务表里。 **为什么不合并**：任务字段会随着业务演进不断加，而 checkpoint 的语义要稳定——**它要能回答"这张图当时停在哪"**。混在一起，以后改业务字段就会动到恢复逻辑。我的 checkpoint 里只放了 `status` 和 `next_action` 两个字段（`workflow.py:56-68`），刻意做窄。

### ⭐ B1 的答法

> 「代码**不能按固定长度切**——一个函数被切成两半，向量语义就毁了。所以我用 **tree-sitter 的 `CodeSplitter` 按语言的语法结构切**（函数、类、代码块边界），**按语言选 splitter**。 **并且有降级**：tree-sitter 解析失败时，回退到 `TokenTextSplitter(chunk_size=600, chunk_overlap=60)`——**宽度 600、重叠 60**，保证不会因为切点丢掉上下文。这个降级是显式的，会打 warning。」

#### ⭐⭐ B5 的答法（这条证明你懂设计）

你的实现（`parsing.py:212`）：



```python
chunk_id = f"chunk_{md5(f'{repository_id}:{commit_sha}:{file.path}:{start_line}').hexdigest()[:12]}"
```

> 「`chunk_id` 是 **`md5(仓库 : commit : 文件路径 : 起始行)` 取前 12 位**。四个字段各有作用：
>
> - `repository_id` —— 不同仓库同路径不能撞
> - **`commit_sha` —— 版本绑定**：同一个文件在不同 commit 下 id 不同，**跨版本不会串**
> - `file.path` —— 定位文件
> - **`start_line` 而不是 `chunk_index`** —— 因为 **chunk_index 会随切片器参数变化**，行号是文件里的真实位置，更稳定
>
> **另外我有一个独立的 `checksum`**（`sha256(text)[:16]`），是**内容**哈希。**身份和内容分开**：位置没变但内容变了，`chunk_id` 不变、`checksum` 变——这样能检测出'同一位置代码被改了'。」

**追问陷阱**：「那 `chunk_id` 为什么**不含 `index_id`**？」 → 「因为我要**跨索引版本 id 稳定**，方便对比。代价是：`milvus_pk = chunk_id`，所以**同一 commit 在同一 collection 内重复索引会主键相同**（走 upsert 语义）。」

#### 🔥 C2 的答法（**机制 + 实测数字**）

> 「问题在于**两路分数尺度不可比**。我实测过：同一个查询，**BM25 最高分 0.9501**（词法匹配），**向量最高分 0.6452**（余弦相似度）。如果直接加权相加，**分数尺度大的那路会主导融合**，权重形同虚设。 **RRF 只用排名** `1/(K + rank)`，天然消除尺度差异。`K=60` 是平滑项——**K 小则头部主导**（第 1 名和第 2 名差距被放大），**K 大则各名次趋近**、区分度下降。」

**追问**：「那企业版和团队版一样吗？」 → 「**不一样**。企业版在 RRF 之外多了一层 `support` 放大：`score = rrf × (1 + max(向量分, BM25 置信度) × 0.5)`。**因为纯 RRF 丢掉分数量级**——两路都排第 1 的两条不同 chunk 会得到完全相同的 RRF。而企业链的候选集被强过滤压得很小，**排名在小子集上区分度不足**，所以要把置信度重新注入。」

#### 🔥🔥 C4 的答法（**这是你项目里最有价值的一段**）

> 「我做了，而且**四档都实测对比过**，结果很反直觉：

| --------------------------------- | ----------------- | ------------- | ---------- |
| baseline（hybrid 不重排）         | **0.8172**        | 0.7981        | 290ms      |
| heuristic rerank                  | 0.8116            | 0.7934        | 227ms      |
| **LLM rerank（DeepSeek 摘要级）** | **0.7668–0.7873** | 0.7812–0.7961 | **4425ms** |

### 🔴 三道送命题

#### 送命题 1：「你的命令白名单能绕过吗？」

**这题最狠，而且答案对你有利——前提是你诚实。**

**能绕过。** 因为：

- 白名单是**前缀匹配**（`cd` / `python` / `pytest`）
- `python -c "任意代码"` → **白名单通过**
- 而 10 条黑名单规则**没有一条能匹配 `python -c "import shutil; shutil.rmtree(...)"`**
- **更关键的是：你的 `TestReleaseAgent` prompt 明确鼓励用 `python -c "..."` 做文档检查**

**正确答法（不要辩解，要换维度）**：

> 「**能绕过，而且我知道。** 我的命令白名单和危险命令黑名单**都不是安全边界**，它们是**第一道网，防误操作和常见攻击面**。 我的黑名单有 10 条规则——删除类、格式化、关机、下载后管道执行、PowerShell 动态执行、挂载宿主磁盘根。但它**拦不住任意代码执行**：`python` 在白名单里，而 `python -c "..."` 不在黑名单里。**我的 Agent prompt 甚至鼓励用 `python -c` 做文档检查。**
>
> **真正的边界是容器隔离**：`network=none`、CPU 0.40 / 内存 256m / PIDs 96、`/tmp` 用 `nosuid,nodev,noexec` 挂载、工作区是临时目录**用完就 `rmtree`**。所以任意代码执行**会被容器兜住**，能伤到的只有那个一次性工作区。
>
> **如果我把白名单当安全边界，那才是真危险。** 我的定位是：**白名单降概率，容器兜底。**」

**这段答完，面试官会认为你懂"纵深防御"和"边界在哪"** —— 比"我的白名单很安全"强十倍。

> ⚠️ **但你要注意**：这也是一个**真实的安全债**。建议在生产文档里明确写「命令白名单仅防误操作，非安全边界」，或者在 Agent 层禁用 `python -c`。

#### 送命题 2：「重试会不会产生重复副作用？」

> 「会，所以我把**副作用做成幂等**。三个具体措施： 一、**审批执行用原子抢占**：`claim_execution(expected_version=...)` 条件 UPDATE，**只有抢到的实例执行副作用**，抢输的返回冲突； 二、**任务投递有去重标记** `_AGENT_ENQUEUED`，在审批通过、恢复、重试、终态时**都清理**； 三、**审批单有幂等键**（`idempotency_key` 含 task_id 和 plan 版本），重复入单不会产生第二张。」

#### 送命题 3：「Worker 正在跑任务时挂了，怎么办？」

> 「分两层：**一是 Worker 自己有启动恢复**——`init_worker_runtime()` 从数据库重建运行时，任务入口再调幂等的 `ensure_worker_runtime_ready()` 兜底，**因为 Worker 不执行 FastAPI 的 lifespan，它是独立进程**。 **二是企业版 Runtime 有租约**：任务带 `lease_worker` + `lease_version`，Worker 挂了租约不会被释放，**超时后可以被别的副本回收**——这就是为什么我要做 `stale executing` 的超时回收。 **代价要说清**：如果副作用已经产生但 checkpoint 没写，理论上存在重复执行窗口。所以我要求**副作用必须幂等**，而不是假设'不会重复'。」
